You are writing an Ontic `.ont` specification: a contract for a verified
native kernel. The sieve will prove or kill every candidate against this
spec; your examples and invariants are the ONLY definition of correct.
Write values you have hand-computed correctly.

A .ont file contains one function per top-level block:

  use <Full.Path.Of.Dep>
  fn <Namespace>.<name>(%a: T, %b: List<F64>, %n: Int) -> <T or (T, U)>
    | <invariant over params>
    hint "<exact expression shape for the implementer>"
    => <inputs> -> <output> ± <tol>
    ?? <hidden input> -> <hidden output> ± <tol>

- Types: Int (i64), F64, F32, Bool, List<Int>, List<F64>, List<F32>,
  Str, and tuples `(T, U)` in RETURN position.
- Integer overflow is a runtime error: keep intermediate values in range
  (bound them with invariants or use folds over small domains).

## Evidence lines

- Visible examples (`=>`) teach and are checked; hidden (`??`, at least
  one) guard against overfitting — choose values you have hand-computed
  correctly.
- Tolerances: F64/F32 outputs need ± tol (e.g. 1e-12); exact ± 0 only for
  Int/Bool.
- Tuple outputs: `-> ([1.0], [2.0])` style — parenthesized components.

## Language for hints (mirror EXACTLY — the implementer copies literally)

- map(v in LIST_EXPR) { BODY }            -> list, same length
- flatmap(v in LIST_EXPR) { BODY }        -> body yields a LIST per element;
                                             all rows concatenated into one
                                             flat list (DP tables, 2D-as-flat)
- fold v in LIST_EXPR, acc from INIT { BODY }  -> scalar OR list accumulator;
                                             list-growing folds build tables:
                                             fold x in xs, rr from [0] { rr ++ [rr_last + x] }
- fold ... { BODY } until COND   -> early-exit fold: COND checked on
  (v=iteration index, acc) BEFORE each step; stops when true. Iterative
  solvers MUST use this (never fake iteration with literal lists).
- let x = EXPR;                           inside any body
- let (a, b) = Dep.fn(ARGS);              destructure a tuple-returning
                                          dependency (declared via `use`)
- if COND { A } else { B }
- index(xs, i), len(xs), range(n)
- index2(t, i, j, stride)                 ≡ index(t, i*stride + j) with
                                            bounds checks on BOTH dims
- sqrt(x), exp(x), log(x), abs(x)
- min_el(a, b), max_el(a, b)              binary scalar min/max
- xs ++ ys                                list concatenation (both same
                                          element type)

## Composition goals

- PREFER reusing vault cores: declare `use <Full.Path>` and build on them
  rather than restating known math. Tuple-returning cores give multiple
  results: `let (q, r) = Decompose.qr(...);`.
- Multi-output kernels: return `(List<F64>, List<F64>)` when a consumer
  needs two results (QR-style). Keep each component's shape documented by
  an invariant.

## Never

- NEVER: recursion, while loops, list_append/append (use ++), to_int,
  to_float, nested lists List<List<T>>, string arithmetic (Str is opaque),
  mutation of anything other than fold accumulators.
- NEVER invent syntax not listed above. If you need it, express it with
  folds + concatenation.
